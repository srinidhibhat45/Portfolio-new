01 The problem

What does it take to recover something a presenter can actually work with?

A PDF preserves how a slide looks but usually loses the convenient objects a presenter wants to edit. DeckForge approaches that gap as a reconstruction problem: recover meaningful text, images, and vector objects, then let a person work with them rather than repainting a screenshot.

Designed for Presenter revising an existing PDF. Recognise editable content and control presentation pacing.

User context Design assumption

Making changes shortly before sharing or presenting a deck.

The friction
A recovered fragment may be selectable without being meaningful.
Design implication
Expose recognisable objects and explain editing limits.

Example situation · illustrative scenario. Imagine needing to revise one text block or animate one diagram, but having only the exported PDF. The visual is preserved; the convenient objects are gone.

02 The outcome

A slide that can keep moving.

The product connects recovered slide objects with editing, sequencing, presentation, and export. My UX focus is what someone can recognise and do with the recovered content, including the explanation of content that remains an image.

More about the experience
  • A working reconstruction tool. The capture introduces the actual editor workflow.
  • An honest fallback. Scanned or dense pages can remain usable raster layers.

03 The direction

Objects should be recognisable

Recognisable objects make editability useful. Text, paths, and images need to become meaningful layers rather than a pile of drawing instructions.

Product artifact · slide editing journey

My direction. I framed the journey around recognising an object, revising it, and presenting it, with an explanation when recovered content cannot be edited.

Process and product scope

I framed the editor around objects a presenter can recognise: a text block, a logo, a shape, or a chart. A technically selectable fragment is not useful if its meaning is unclear.

The flow needs to explain what can be edited, preserve a usable slide when recovery is limited, and distinguish live presentation pacing from an exported recording.

04 Design decisions

Make the PDF’s editable parts understandable.

Open a decision to see the reasoning and trade-off.

01

Make layers correspond to recognisable objects

+

Paths are grouped into likely logos, dividers, shapes, and chart series, while text is reconstructed into blocks.

Why this matters. An editable layer is useful only if the person recognises what it represents.

The trade-off. Object recovery is heuristic. Preserving appearance can be more valuable than forcing misleading editability.

02

Let a presenter control the pace

+

Animations can wait for an advance action, while timed outputs play sequentially.

Why this matters. A live talk and an exported recording need different behaviour from the same slide.

The trade-off. That difference must be visible before export so the presenter knows what an audience will receive.

03

Keep the core document workflow local

+

PDF reconstruction and editing run in the browser; phone pairing has a separate connection mechanism.

Why this matters. Local processing supports a lightweight workflow and avoids requiring a document-upload service.

The trade-off. Phone pairing still uses signalling, and some remote features exchange preview frames. The privacy explanation should distinguish those paths.

05 Reflection

Recover enough structure to make the next action possible.

The useful boundary is between faithful recovery and an honest fallback. A tool that explains why part of a page remains an image can be more trustworthy than one that claims every object was successfully recovered.

What I would evaluate next proposed work
  • import a defined set of native-text, scanned, multi-column, and dense-vector PDFs; record editability and visible fidelity separately.
  • revise a real slide and present it, measuring manual corrections and surprises between editor, audience view, and exported output.
